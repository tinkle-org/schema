The `tinkle.v1` package is the public Protobuf contract of the Tinkle messaging
API. Its single source of truth lives in this repository under
[`tinkle/v1/`](https://github.com/tinkle-org/schema/tree/main/tinkle/v1) —
there is no upstream mirror; every contract change is authored here.

## What is published where

| Layer | Location | Rebuilt on |
| --- | --- | --- |
| Protobuf source | `tinkle/v1/*.proto` in this repo | Commit |
| Validation (lint/format/breaking/build) | GitHub Actions on every PR | Every push |
| Schema distribution (Go/Rust SDKs) | [Buf Schema Registry](https://buf.build/tinkle-org/schema) | Matching `main` pushes and `v*` tags |
| This documentation site | Generated reference served by the main website at `tinkle.me/schema/` | Website image build |

The Buf CI workflow validates every PR and posts a summary, and publishes
`main` pushes matching its paths to the BSR; `v*` tag pushes publish version
labels.
[release-please](https://github.com/googleapis/release-please) manages versioning
and release tags.

The [schema reference](/schema/reference) is produced from the protobuf
descriptor set, including source comments, deprecations, and reserved
definitions, on every site build. Edit `.proto` doc comments to change the
reference and `website/content/` for schema overview pages.

## Schema scope

The package defines authentication, accounts, users, contacts, messaging,
channels, bots, stickers, and help APIs, with shared types in `common.proto`.
`entities.proto` defines the single `Entity`/`EntityType` vocabulary for help text,
message bodies, captions, drafts and quotes. Spans use UTF-16 code units with
Unicode scalar boundaries, explicit nesting/overlap rules, and type-specific
fields. Custom emoji pin `custom_emoji_id` plus an exact `asset_version`; their
canonical `fallback_text` must exactly match the selected text span. Reactions
pin the same asset identity/version with canonical fallback in `emoticon`.
`GetStickerAssets` resolves exact versions in batches; retained fallback text
remains renderable when an asset is unavailable.

[`auth.proto`](https://github.com/tinkle-org/schema/blob/main/tinkle/v1/auth.proto)
defines phone verification and recoverable device-key enrollment. See
[Device Enrollment](/schema/device-enrollment) for protected key delivery,
capability-authorized storage acknowledgement over pinned Bootstrap, activation,
rotation, and fresh ACTIVE-key Returning authentication. STAGED keys cannot pass
Returning admission. Account session identifiers are neutral device-session UUIDs.

[`connection.proto`](https://github.com/tinkle-org/schema/blob/main/tinkle/v1/connection.proto)
defines `ConnectionService.InitConnect`, pairing a full `ClientInfo` snapshot
with a selected public unary call, and `ConnectionService.KeepAlive`, observing
ACTIVE-authenticated application liveness with a channel-local sequence and
current authorization before presence-lease effects. Duplicate sequences do not
renew a lease; runtime bindings own scheduling and deadlines. See
[Connection Initialization](/schema/connection-initialization) for validation,
authorization, replacement semantics, and persistent versus request-scoped
binding requirements. Runtime bindings and Chorus adapters for this contract
are not implemented here; the schema does not establish runtime availability.

[`files.proto`](https://github.com/tinkle-org/schema/blob/main/tinkle/v1/files.proto)
defines `FilesService` — resumable upload sessions, authoritative status,
atomic completion, and byte-range downloads — with the shared media
vocabulary in `media.proto`; see [File Transfers](/schema/file-transfers).
[`updates.proto`](https://github.com/tinkle-org/schema/blob/main/tinkle/v1/updates.proto)
defines `UpdatesService`, now streaming only ephemeral privacy-filtered
per-user `ConnectivityChanged` observations through `ObserveConnectivity`;
durable replay and watch (the former `ReadUpdates` and `FollowUpdates`) have
been retired from the public contract and remain implementation-internal.
`messages.proto` carries reconciliation primitives for clients without a
durable feed: `GetMessages` batch-fetches messages by ID, `Message.accept_seq`
orders and dedups per conversation, `ListMessageChanges` lists authorized retained
body/metadata changes and removals after a mutation acceptance position, and
`GetHistoryResponse.more_available` provides server-confirmed pagination.
Complete-body freshness uses `Message.body_revision` for the same authenticated
principal and message, not the original acceptance position. User `edit_date`
is only a fallback when a revision is absent; metadata changes do not create edit
dates. A marker's `message_revision` records its exact event revision, while its
authorized hydrated body can be newer. Journal pagination uses the returned stable
`last_accept_seq`, with no continuity guarantee across filtering, retention or
pending positions. `MessageChanged` and `TypingChanged` are typed notification
payloads, not additional RPCs, durable cursors, receipts or transport bindings.
Private ACK markers/hints are disclosed only to their own viewer.

The 43-method `MessagesService` includes explicit actor-owned scheduled-message
lookup/cancellation and sender-owned poll closing. `GetScheduledMessages` requires
exactly one nonempty set of 1..100 distinct positive message IDs or nonzero signed
idempotency keys in one conversation; it does not discover a job list. Unknown,
unowned and expired jobs are omitted. Job status alone proves neither accepted
history nor peer receipt. `CancelScheduledMessages` accepts 1..100 distinct positive
message IDs and expands selected album groups. Its durable canceled results are
not rollback or a batch transaction; accepted history is never deleted. Reconcile
uncertain or partially applied calls through explicit lookup.
`ClosePoll` returns the existing caller-relative poll projection. Quiz correctness
is hidden until the caller votes or the poll closes, not exposed by a separate key.

`TargetChange.body_invalidated=6` is explicit source-authorized nonterminal body
withholding for the canonical caller/target/message identity. With no body and a
positive revision, purge cached bodies/file references at or below that revision
and retain a nonterminal revision floor. Stale/unknown held responses cannot
restore them; fresh currently authorized bodies at the same or newer revision
can hydrate. This is not viewer deletion or permission proof.
`MessageChanged.body_invalidated=6` is a non-authoritative hint to reconcile with
the current source, not authority to apply a floor or to read files.

`SendAlbum` accepts atomic ordered album items; `GetChatDetails` returns enriched
`ChatDetails` in `response.chat_details`, `ListThreadMessages` lists thread replies, and reaction reads use
`BatchGetMessageReactions` and `ListMessageReactions`. `MarkHistoryRead`, `StartBot`
and `UpdateChatDescription` describe their actions directly. The description write
uses `request.description`; the shared basic entity retains `Chat.about`. Send deduplication
uses `int64 idempotency_key`, scoped to the authenticated principal and target;
thread/reply fields use `thread_root_id` and `reply_to_message_id`.

`CreateChatRequest.operation_id` must be a positive `int64` when `ttl_period > 0`;
zero selects an unkeyed request only with absent/zero TTL.
`AddChatParticipantRequest.operation_id` must be a positive `int64` when
`forward_limit > 0`; zero selects an unkeyed add only with zero forward limit.
Negative keys are invalid. Keep numeric room keys distinct from reaction/history
UUID strings and retain original keys/arguments after uncertain completion.

`SetMessagePin.pin_scope` separates shared and personal pins. Omission selects
shared pins; explicit unspecified values are rejected. `Message.pinned` is shared;
optional `Message.personal_pin` is caller-private and optional
`Message.suppress_link_preview` reports link-preview suppression. An absent
optional projection is unknown, not false. Personal pin changes use viewer-only
ACK changes and never disclose another principal's private state.

`DeleteHistory` uses a client-persisted `operation_id` and explicit
`completed`/`processed_count` progress on the existing method. Retry
identical requests with the same ID until completion; timeouts do not prove
rollback. History selection freezes at the first accepted call, so later messages
are not swept into retries. With `revoke=true`, the caller's own messages are
removed for everyone, incoming messages for the caller only. No general job API
or authority to revoke another sender's messages is implied.
`DeleteMessages` evaluates items independently and reports only the count newly
deleted by that call. Unknown, inaccessible or ineligible items do not prevent
deletion of eligible items; no operation ID or progress fields are required.

Participant restrictions distinguish text, photo, video, audio, voice and raw
document sends without collapsing them into one media flag. Favorite-sticker
writes carry desired `is_favorite` membership: true adds, false removes.

`SendReaction.operation_id` is a caller-scoped UUID required for true `animate`
or `save_to_recents` options. Absent/false options leave those side effects off.
`GetRecentReactions` reads only the caller's at-most-32 retained exact identities.
`MessageChanged.reaction_effect` carries an actor, operation UUID, fixed expiry
and exact reaction choices. Recheck recipient visibility, deduplicate by actor and
operation, and discard expired effects; neither reconnect nor hydration restarts
an animation or extends its expiry. Retained identities grant no asset access.
Presentation requires a validated positive actor, canonical UUID and finite
unexpired deadline; invalid metadata never triggers animation.

Text/media/album sends carry optional `clear_draft_dialog_id` and
`clear_draft_revision` tokens. Clearing is limited to the authenticated sender's
exact source pair, retained unchanged on retry, for immediate and scheduled sends
in direct conversations and rooms. `Dialog` reports its owned pair
even when draft content is absent; initialized empty sources have revision zero,
while missing tokens mean unknown. Newer drafts must not be cleared by late retries.
`Dialog.notification_settings` carries owner-resolved preferences without turning
absence into an enabled default. Optional unread mention/reaction counts preserve
known zero separately from unknown. Optional `read_outbox_max_id` is a DM message
reference, not an ordering position; unsupported or unknown projections omit it.

Ordinary `DeleteHistory` deletion affects the caller only, leaving the peer's
history and read state unchanged. Recovery keeps the original filters and frozen
source selection, not a selection rebuilt from later caches or peer history.
Participant views are independent: caller-only deletion leaves another participant's
copy intact and proves neither physical byte erasure nor unrelated message deletion.

Search returns full `Message` bodies in a shared `SearchResponse`. Its `source`
is `SERVER` or `CACHE`, and `coverage` is `INDEXED` or `CACHED_SUBSET`; unspecified
or absent metadata means unknown. `more_available` reports only the selected
backend's continuation, so an exhausted cache still covers only a cached subset.
Queries are literal case-insensitive substrings of message text/captions, without
regex, wildcard or token syntax, bounded to 1024 UTF-8 bytes. Page size is 1..100,
with zero selecting 50. Unicode case handling and searched corpora can differ by
backend; identical matching is not guaranteed. Results use stable descending
source acceptance order within a target/source and a source-defined deterministic
global order with target/message identity tie-breakers. Acceptance positions from
different targets are not comparable. Continue with the selected source's cursor.
Recovery keeps the same source and original filters; a changed source or filter
starts a search without reusing a continuation.
See the [reference](/schema/reference) for the contract details.

This repository documents the transport-independent schema. Runtime transport
bindings belong in their implementation repositories. Public UpdatesService
bindings are not implemented in Chorus; internal replay, watch, and presence
capabilities exist.

## Status

The contract is **pre-release**. `buf.yaml` disables builtin breaking checks for
`tinkle.v1` restructuring; the intended stable policy is `breaking: FILE`, to be
re-enabled at the first stable release. Until then, structural churn and no
external compatibility commitment are expected. The generated reference follows
`main` and may be ahead of the latest published SDKs.
