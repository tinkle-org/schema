# File Transfers

`tinkle.v1` keeps file transfer independent of messaging.
[`FilesService`](/schema/reference/services/files) owns resumable upload
sessions, authoritative upload status, atomic completion, and byte-range
downloads. Every other service — messaging, profiles, stickers, bots —
references completed files by their canonical `file_id`, so one upload can
back many attachments across services.

## Upload lifecycle

```text
BeginUpload ──► UploadPart(0 … n-1) ──► CompleteUpload ──► FileInfo { file_id }
                    │      ▲                      │
                    │      └── re-upload missing ─┤
                    └─ reconnect: GetUploadStatus ┘
```

The client declares the exact total size and an optional whole-file SHA-256
digest when opening the session; the server returns the negotiated part
size, parallelism allowance, and expiry. Parts are zero-based and exactly
the negotiated size except the final part. Completion verifies every part
and the exact size, computes the authoritative digest, and publishes the
file atomically — a failed completion never yields a partially valid file.

A completed upload is only the first half of the story. Attachments are
built in three steps, and the contract keeps them separate on purpose:

1. **Process and upload the main bytes** for the explicit purpose —
   `BeginUpload` → `UploadPart` → `CompleteUpload` yields a canonical `file_id`.
2. **Construct the typed attachment** — a `PhotoSource`, `DocumentSource`,
   `VideoSource`, `AudioSource`, `VoiceSource`, or `StickerSource`
   referencing that `file_id`, with client-declared metadata and variant
   references. `BeginUpload` carries only optional generic `processing_intent`,
   not physical media metadata: attachment
   semantics belong to the `*Source` types, and `FileInfo` stays limited
   to immutable storage facts.
3. **Send or edit the application object** — validate main bytes independently of
   optional thumbnails. Ordinary owning methods can return private pending work,
   then accept the validated main and later attach optional representations.

Client-declared MIME types, dimensions, durations and codecs are non-authoritative
claims. Typed authoring measures physical facts from completed bytes and rejects
mismatches. File names and MIME declarations do not select a media purpose.
File-level encryption is not supported: this contract exposes no encryption
options or key material.

| Step | Contract |
| --- | --- |
| Session creation | `BeginUpload` with `idempotency_key` scoped to the caller; identical retries return the same session and conflicting parameters are rejected; terminal sessions resolve per the server-defined retention window before the key may be reused |
| Parts | Zero-based indexes; identical resubmissions succeed, conflicting bytes for a confirmed index are rejected |
| Status | Confirmed part ranges are authoritative server confirmations, never echoes of client submissions |
| Completion | Atomic; repeated completion returns the same committed file |
| Cancellation | `AbortUpload` is idempotent best-effort cleanup and never deletes a completed file |
| Expiry | Server-defined, returned in the session response; expired sessions can neither resume nor complete |

## Idempotent session creation

The idempotency key is scoped to the authenticated principal and bound to
the exact request parameters. Equivalence is exact: optional fields compare
by presence as well as value, so an omitted optional field and one set to
its empty value are different parameters and conflict.

`BeginUploadRequest.processing_intent` is optional: `IMAGE` requests image
inspection and `VIDEO` requests video inspection, only after durable upload
completion. Explicit `UNSPECIFIED` and unknown values are invalid before key
binding. Presence and exact enum value participate in idempotency: omitted,
`IMAGE`, and `VIDEO` are distinct inputs. The intent is fixed for the session
and completed file, grants no access, and never authorizes main transcoding.
Completion still returns only immutable storage facts without waiting for a
worker. For new typed image/video authoring, require the matching intent; raw
documents, audio and voice require omission. MIME/name/sniffing never select it.
Capturing an already validated exact catalog asset version is exempt from the
upload-intent requirement; it does not require re-uploading that version's main.

A retry with the same key resolves to the retained session, and
`BeginUploadResponse.status` says which outcome that is — clients decide
solely on this field and never infer terminal state from absent or
zero-valued configuration:

| Status | Meaning | `part_size_bytes` / `max_parallel_parts` / `expires_at` | `file` |
| --- | --- | --- | --- |
| `UPLOAD_STATUS_ACTIVE` | New or still-active session | Present | Absent |
| `UPLOAD_STATUS_COMPLETED` | The retained session already committed | Absent | Present |
| `UPLOAD_STATUS_ABORTED` | The retained session was cancelled | Absent | Absent |
| `UPLOAD_STATUS_EXPIRED` | The retained session expired | Absent | Absent |

The configuration fields apply only to active sessions; for terminal
outcomes they are omitted, not zero-filled. `upload_id` is always present
and identifies the retained session. Terminal sessions are retained for a
server-defined window; after retention, the key may be reused for a new
session.

**Zero-byte uploads** have no parts and complete immediately: `BeginUpload`
returns `UPLOAD_STATUS_COMPLETED` with the committed `FileInfo` directly.
The server validates the declared digest before completing — a `sha256`
declaration that disagrees with the empty-sequence digest is rejected at
creation. That `FileInfo` carries `size_bytes` 0 (which serializes as
absent under the contract's implicit-presence convention) and the
server-computed SHA-256 of the empty byte sequence,
`e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`. A
client that ignores the status and calls `CompleteUpload` anyway still
succeeds idempotently with the same file.

## Part sizes and transport limits

New sessions select **64, 128, 256 or 512 KiB** (65536, 131072, 262144 or
524288 bytes), uniformly across all media types. The server negotiates
**one exact part size per session** at creation,
sized to fit the deployment's maximum transport message size with protobuf
framing and envelopes included, and persists it for the session's
lifetime. If no allowed size fits, session creation fails:

- Every non-final part must be exactly the negotiated size; the final part
  must exactly complete the declared total size. Wrong-size parts are
  rejected.
- The contract's parts are application-level units. They are not storage
  upload parts: servers may segment, buffer, or re-group the bytes however
  their object storage requires, and no storage-internal identifier,
  marker, or checksum ever surfaces in this contract.
- A resumed session keeps its original part size. If a caller's current
  transport cannot carry the negotiated size, the caller must not resume
  with that transport — the boundary never silently changes, and
  `GetUploadStatus` echoes the size so the client can detect the mismatch
  before uploading.

Download limits are discoverable per deployment: `GetFileInfoResponse`
carries `max_download_part_bytes`, the largest data payload a single
`DownloadPart` call may request. It is response/transport information, not
an immutable `FileInfo` fact — it may differ between deployments and change
over time, which is why it lives on the response rather than in `FileInfo`.
Its type matches the request limit, so an advertised bound is always
requestable. Servers must set it for every file they serve; when it is
present, a `DownloadPart` request above it is rejected, and when it is
absent — a non-conforming response — clients must fall back to a
conservative limit of their own choosing, with only nonpositive limits
rejected. A server may still return fewer bytes than an in-range limit to
respect its current transfer budget, and clients continue from
`offset + len(data)`, never from the requested limit.

## Recovering an interrupted upload

An interrupted upload recovers from status alone — the client does not need
to keep its own progress log, only the `upload_id`:

```text
BeginUpload            → upload_id = "up-123", part_size = 256 KiB
UploadPart(0), (1)     → confirmed
UploadPart(2)          → connection lost
GetUploadStatus        → ACTIVE, received_ranges [(0,2)]
UploadPart(2)          → confirmed
CompleteUpload         → FileInfo { file_id }
```

Ranges are half-open: `(0,2)` covers parts 0 and 1 — the start index is
inclusive and the end index exclusive.

When `CompleteUpload` is called with parts missing, it fails with a
structured incomplete-upload error carrying the missing ranges (bounded,
with a truncation flag). `GetUploadStatus` always provides the same
information, so recovery does not depend on error details being preserved
by the transport — a client whose transport drops error details treats
any failed completion as "consult `GetUploadStatus`".

Part uploads have the same ambiguity rule in reverse: a timed-out or
disconnected `UploadPart` proves nothing about the part's fate. Transport
failure never reverses a committed part, so while the session is active
the client resubmits the identical part (which succeeds idempotently if
it had committed) or consults `GetUploadStatus`. An acknowledgement always
means durable acceptance — a part that is only queued in memory is never
confirmed, and confirmed parts survive process restarts and requests
routed to any replica. Once the session is terminal, `UploadPart` rejects
even identical retries of previously confirmed parts; recovery then goes
through `GetUploadStatus` and, for committed sessions, `CompleteUpload`.

## Status is a snapshot

`GetUploadStatus` enumerates confirmed part ranges from one stable
snapshot. Continuation tokens bind the snapshot, the session, the caller,
and an expiry: new acknowledgements never shift or merge ranges across
pages of that snapshot, so paging during an active upload cannot skip a
confirmed range. The whole response is snapshot-consistent — `status`,
`received_ranges`, `size_bytes`, `expires_at`, `part_size_bytes`, and
`file` all come from the same snapshot — and new parts or terminal
transitions never produce contradictory pages: pages issued from an active
snapshot keep reporting that snapshot's state, and only a fresh first-page
request observes a terminal outcome. Expired or invalid tokens fail
explicitly and pagination restarts from the first page; servers bound
snapshot retention and page size as implementation policies. Every
response carries the declared total size; active sessions additionally
carry the negotiated part size and current expiry, both absent after a
terminal transition — enough to resume after losing local upload state.

## Completion, races, and recovery

`CompleteUpload` verifies every required part and the exact total size
before publishing. `FileInfo.sha256` is the SHA-256 of the complete stored
bytes in order — never a storage-layer upload identifier or composite
checksum. Optional expectations from `BeginUpload` and `CompleteUpload`
must agree with the server-verified digest; a mismatch fails the
completion and never publishes the file. The two mismatches differ in
recovery: a `CompleteUpload`-supplied mismatch is retryable — re-check
status and retry with a corrected or absent expectation — while a
`BeginUpload` declaration is fixed for the session's lifetime, so an
unsatisfiable declaration can never be corrected and the client must
abort the session and start a new upload.

Atomic completion means atomic *application visibility*: the file becomes
visible to authorized readers together with its canonical `FileInfo` in a
single step, after its bytes are durably stored. It does not imply a
distributed transaction between metadata and object storage.

Timeouts are ambiguous by nature. A timed-out, cancelled, or disconnected
completion call proves nothing — the commit may have happened, and a
deadline does not establish rollback. Recovery is always the same: call
`GetUploadStatus` (a committed session reports `UPLOAD_STATUS_COMPLETED`
with the committed `FileInfo`), then retry `CompleteUpload`, which is
idempotent and returns the same committed file. Concurrent successful
completions resolve to one committed `file_id`, and exactly one terminal
outcome wins when completion races abort or expiry.

## Identifiers

Three identifier kinds appear in and around the file contract, and they are
not interchangeable:

| Identifier | Kind | Lifetime | Notes |
| --- | --- | --- | --- |
| `upload_id` | Temporary session reference | Until expiry, abort, or completion | Bound to the uploader; opaque `string`; never a `file_id` |
| `file_id` | Canonical file reference | Immutable after completion | Opaque `int64`, globally unique, never reassigned; exposes nothing about storage internals |
| `id` on `Photo` / `Document` | Domain-object identifier | Per attachment object | A photo/document object references files; it is not itself a file ID |

Possessing any of these identifiers grants no access. Every metadata
retrieval and download passes an access check per call.

## Sources and results

The media contracts use a naming convention that separates what clients
provide from what servers return:

| Convention | Meaning | Examples |
| --- | --- | --- |
| `*Source` | Client-provided content definition for an operation | `MediaSource`, `PhotoSource`, `DocumentSource`, `VoiceSource` |
| Media objects | Server-returned attachments | `Photo`, `Document`, `Media` |
| `FileInfo` | Authoritative storage facts about committed bytes | `files.proto` |

File-backed sources (`PhotoSource`, `DocumentSource`, and the typed
`VideoSource`, `AudioSource`, `VoiceSource`, `StickerSource`) always
reference an uploaded, completed Tinkle file — never a local path, URL, or
unfinished upload. Their physical metadata is a client claim that the server
checks against measured bytes. `DocumentSource` with no attributes is a raw
document: retain its bytes unchanged, without automatic classification, media
normalization or preview generation based on sniffing. Explicit `MediaAttribute`
entries select typed purpose and its validation policy; duplicate or incompatible
attributes are rejected. The typed sources select the same policies. Sending an
image as a raw document does not implicitly select photo handling.

Thumbnail inputs (`ThumbnailSource`) are optional completed, caller-owned files,
access-checked like every other file reference. They are processing inputs, not
validated output facts. Accept at most one static thumbnail input,
with both dimensions positive; mismatched bytes are rejected.
Valid supplied thumbnails are adopted under their exact file IDs. Invalid supplied
inputs fail the owning action, never silently disappear; omission is valid.

## Main media processing and validation

Clients process the main file before upload. At typed authoring, the server
applies the purpose's versioned policy and publishes measured metadata with the
applied `MediaValidation` profile/version. General source metadata may be omitted;
validation is still mandatory. Explicit unsupported versions, unspecified or
purpose-mismatched profiles, and inconsistent physical claims are rejected.
Raw upload completion alone does not validate application media.

All profiles below use version `1`:

| Purpose | Profile | Main output |
| --- | --- | --- |
| Message/chat image | `IMAGE` | Static PNG or static/animated lossless WebP; at most 10,000,000 bytes and positive width/height each at most 10,000 pixels. |
| Video | `VIDEO` | MP4 with H.264 8-bit 4:2:0 video and optional AAC-LC audio only; positive rotated display dimensions, long edge at most 1920 and short edge at most 1080. |
| Audio | `AUDIO` | Audio-only MP4/M4A with AAC-LC and positive duration, no video track. |
| Voice | `VOICE` | The same audio-only AAC-LC container rules, with voice purpose retained separately. |
| Sticker/custom emoji/profile photo | `STRICT_LOSSLESS` | Static PNG or static/animated lossless WebP, subject to the tighter domain bounds below. Profile photos are static. |

Automatic main-image resizing is permitted to meet both the 10,000,000-byte bound
and the 10,000-pixel bound on each dimension, preserving aspect ratio without
upscaling. Losslessness refers to encoding the final resized pixels, not retaining
the original resolution. Tighter domain bounds still apply. Animation must remain
animated lossless WebP unless the user explicitly chooses a still image. WebP
image/frame payloads use lossless encoding; the container name alone proves
nothing about losslessness. Video normalization preserves aspect ratio without
upscaling and keeps the source frame rate unchanged. The output alone cannot
prove the original frame rate or a user's still-image choice; those remain client
processing obligations, not server attestations. Servers validate the normalized
output, not a claimed source history. Transfer/resource limits remain deployment
policy; no general video/audio byte, duration or bitrate limit is implied here.

### Optional thumbnails

Every thumbnail is optional. Validate main bytes independently of generated sizes;
missing or failed generation never blocks or reverses main acceptance. A supplied
thumbnail is a completed file with validated static PNG/lossless WebP bytes and
measured dimensions, adopted under its exact ID. Invalid supplied inputs fail the
owning action, never silently disappear. At most one thumbnail is linked per
main. There is no thumbnail role selector or collection.

`ThumbnailSource` and returned `Thumbnail` each have exactly `int64 file_id=1`,
`uint32 width=2`, `uint32 height=3`. The scalar dimensions have no optional
presence: when the enclosing message is present, all three values must be
positive. Missing or zero dimensions are invalid, not thumbnail omission.
Omit the entire message when no thumbnail is supplied/ready. Returned dimensions
are measured from the validated bytes, not copied from claims.

This clean breaking cutover removes every retired `variants` field and the
duplicate `StickerView.thumb_file_id`, without reserved numbers or names. The
entire public schema uses consecutive declaration-order tags from 1 per message,
including oneof members and independent nested-message sequences. Empty messages
stay empty; enum `UNSPECIFIED = 0` values remain. Old wire slots are deliberately
reused, with no compatibility aliases. All consumers must regenerate together;
old protobuf payloads/caches require an explicit migration or reset before use.
The singular fields use these compact tags:

| Message | `thumbnail` type/tag | `inline_preview` tag | `representation_revision` tag |
| --- | --- | --- | --- |
| `PhotoSource`, `DocumentSource`, `VideoSource`, `AudioSource` | `ThumbnailSource` / 4 | 3 | — |
| `StickerSource` | `ThumbnailSource` / 6 | 5 | — |
| `ProfilePhotoSource`, `StickerAssetSource` | `ThumbnailSource` / 4 | 3 | — |
| `Photo` | `Thumbnail` / 9 | 7 | 8 |
| `Document` | `Thumbnail` / 10 | 8 | 9 |
| `ChatPhoto` | `Thumbnail` / 7 | 5 | 6 |
| `UserPhoto` | `Thumbnail` / 5 | 3 | 4 |
| `ProfilePhoto` | `Thumbnail` / 8 | 6 | 7 |
| `StickerView` | `Thumbnail` / 11 | 9 | 10 |

| Purpose | Thumbnail | Bounds |
| --- | --- | --- |
| Message photo/video | Optional | At most 320x320, 256 KiB |
| Chat/profile photo | Optional | At most 160x160, 256 KiB |
| Sticker/custom emoji | Optional | At most 128x128, 256 KiB |
| Audio cover/raw document preview | Optional explicit supplied input only | At most 320x320, 256 KiB |
| Voice | None | Thumbnail inputs and inline preview are rejected |

Preserve aspect ratio with integer-pixel rounding, never upscale, and use strictly
fewer pixels than an image/video main display frame. A one-pixel main has no
thumbnail. Audio/raw-document covers have no main display dimensions to compare.
Automatic optional generation inspects only explicit image/video intent; no
audio/voice worker, video output, or main transcode is promised. Raw documents
remain unclassified. Do not replace an adopted client thumbnail. Reuse requires
the same immutable main, purpose, profile/version and any explicit cover inputs.

### Ordinary domain pending lifecycles

There is one contract, with no version opt-in, generic operation service, or extra
submission call. `SendMedia`, `SendAlbum`, `EditChatPhoto`, channel `EditPhoto`,
`SetProfilePhoto` and `CreateStickerAsset`/`UpdateStickerAsset` can return durable
private pending image/video validation directly. Physical validation profile
versions remain `1`. No audio/voice asynchronous worker is implied. Scheduled
sends, message edits and bot actions validate before their existing acceptance;
they do not use these pending lifecycles and still use optional thumbnails.

| Owner | Original mutation identity | Response snapshot | Query / cancellation |
| --- | --- | --- | --- |
| Messages | Existing signed nonzero `idempotency_key`; ordered distinct keys for albums | `send_status: SendStatus` | `GetSendStatus` / `CancelSend` with `target` and any one original key |
| Messages chat photo | Existing positive numeric `operation_id` | `photo_update: ChatPhotoUpdate` | `GetChatPhotoUpdate` / `CancelChatPhotoUpdate` with `chat_id`, `operation_id` |
| Channels photo | Direct `request_id` | `photo_update: ChannelPhotoUpdate` | `GetPhotoUpdate` / `CancelPhotoUpdate` with `channel_id`, `request_id` |
| Account photo | Direct `request_id` | `photo_update: ProfilePhotoUpdate` | `GetProfilePhotoUpdate` / `CancelProfilePhotoUpdate` with `request_id` |
| Stickers asset | Direct `request_id`; original `asset_id` for updates | `asset_change: AssetChange` | `GetAssetChange` / `CancelAssetChange` with `request_id`, optional `asset_id` (required for update, absent for create) |

New string request IDs are canonical lowercase nonzero UUIDs scoped to the actor;
persist before the first call. Required on profile sets, channel new-photo actions,
asset creates and source-replacing updates. Metadata-only asset edits remain
synchronous; an optional supplied ID uses the same deduplication/status contract.
New chat/channel photo actions support both the direct completed-file and full
photo source forms. Removal is synchronous with no status; channel removal omits
`request_id`, and chat removal uses `operation_id=0`. Removing a current photo does
not cancel an earlier pending update: use its cancel method and reconcile.
Both chat and channel new-photo actions capture the current photo generation at
binding; final acceptance fails precondition instead of overwriting an intervening
replacement/removal. Existing profile/asset CAS tokens likewise remain fixed.
Immediate file-backed sends/albums always include status, even on immediate
success; scheduled and non-file sends retain their existing response contract.

The domain owner durably records the original actor, method/scope, exact original
request bytes, all send keys in order, immutable sources and claims, preview and
thumbnail inputs, captions/entities/replies/options, CAS and draft tokens **before
returning PENDING**. Persist and retry exact bytes, not reserialized equivalents
or reconstructed cache data. Forwarding preserves the original method payload.
Reject unknown fields recursively before binding; syntactic rejection consumes no
keys. Fingerprints remain internal, not public fields or lookup keys. Reusing a
bound key/ID with different bytes/method/scope conflicts. Every album member key
binds the entire ordered request; another key or UUID cannot bypass it.
Recover existing bindings before fresh CAS/source checks; a terminal retry cannot
fail merely because its original CAS is now old, nor reapply a completed mutation.

Each family has its own state and failure enum: `PENDING` may become `PROCESSING`
or terminal; `PROCESSING` may become terminal. Only `SUCCEEDED`, `FAILED` and
`CANCELED` are terminal, and they never change. Revisions are positive, initially
1, advancing only with state transitions, never with disclosure/enrichment.
Failures are bounded categories, not raw diagnostics. `PENDING`/`PROCESSING` have
**no recipient-visible acceptance**, history, file grant, source mutation, fanout
or draft clear. Workers retain the original actor and source, never fresh CAS or
draft tokens. Before committing, recheck current authorization, file access, main
and supplied inputs, reply/entity/catalog references, original CAS and domain
bounds. Album validation and acceptance are all-or-nothing. Success, deduplication,
accepted identities, owning mutation, exact file membership and durable change/
draft obligations commit atomically. Clear only the captured draft pair on success.

Cancel reports the actual durable outcome: only `CANCELED` proves later effects
are fenced. Claimed work may report `PROCESSING` and still complete; query until
terminal. Cancel unclaimed `PENDING` durably before responding, atomically racing
claim/commit; return terminal or `PROCESSING`, never acknowledge `PENDING` as
canceled. A cancel request never aborts uploads, deletes accepted objects or rolls
back committed selection/head changes. RPC cancellation/deadlines are ambiguous,
not a durable cancel decision. Identical retries recover the same status under
current disclosure policy, not another side effect. No durable gateway is added.

Pending records survive restarts/replica changes and cannot be evicted. Full
terminal outcomes last at least **30 days** from termination (`retain_until`).
Successful identity receipts remain queryable after full-body retention expires.
Deduplication tombstones retain original actor/method/scope, exact-byte binding,
main identities and accepted mapping indefinitely; expiry never permits key reuse.
Unknown, foreign, mismatched and expired non-successful lookups report NOT_FOUND
alike. Get/cancel are actor-only, not discovery or file-access APIs.

#### Acceptance identities are separate from current bodies

`SendStatus.accepted` contains one `SendReceipt` for a single send or **2..10 in
original item order** for an album. Looking up any bound member key returns the
same complete ordered mapping, even after edits/removal. Each receipt has its
original `idempotency_key`, optional `message_id`, optional shared `album_id`, and
an explicit optional-presence `reference_withheld` decision. False requires the
original accepted message ID (and album ID for albums); true omits both IDs but
keeps the slot/key. Pending/processing/failed/canceled have no accepted receipts.

Photo statuses retain the original `photo_id`; asset status retains exact
`accepted: AssetReference`, distinct from its optional original update selector
`asset_id`. Profile status also retains the original commit `gallery_revision`,
not a newly acquired CAS token. Successful photo/asset receipts require an
explicit `reference_withheld`: false discloses the exact original identity, true
omits it. Recheck identity policy on every submit/query/cancel. Ordinary edits or
removal do not erase receipts; disclosure changes do not advance status revision.
Missing decisions/mappings are unknown/nonconforming, never proof of no effect.

Queries separate required status from optional current original matching bodies.
Only success may carry bodies; recheck current source authorization. Omit edited,
removed, superseded, unselected or inaccessible original results; never resurrect
stale bodies or substitute a current photo/asset head. Albums return the complete
matching original body result or none, never partial results or related entities
without bodies. Later representations of the same original main may hydrate.
The same disclosure rules apply to original-method retries. A lost response plus
an intervening edit can therefore report success and receipt IDs without bodies.
Use `GetMessages` for current edited bodies, `GetChats`/`GetChannels`,
`GetProfilePhotos` or exact `GetStickerAssets` to reconcile current source data.
Never send under a fresh key merely because a body/identity was withheld.

### Inline previews and regular thumbnails

`InlinePreview { width=1, height=2, jpeg=3 }` is wired to photo, video, document,
audio-cover, sticker, profile and chat/catalog source/result projections. Both
axes are **1..40** pixels; the JPEG is **1..4096** bytes. Servers require a fully
decoded static single JPEG with exactly matching dimensions, no trailing bytes
and bounded decode work. Clients preserve aspect ratio without upscaling. Empty,
oversized or malformed previews are rejected; omission is valid. This lossy hint
does not relax lossless main validation, create a file ID or carry encryption
flags. It shares its owner's visibility and cannot prove the main contents.
Video results continue using the existing `Document` representation. Raw-document
previews are explicit hints, never automatic media classification. Voice accepts
neither preview nor thumbnail.

Regular optional thumbnails remain separately uploaded completed file IDs in
`ThumbnailSource`. Validate and adopt their **exact IDs** under the
existing per-purpose static PNG/lossless WebP format, dimensions, 256 KiB, single
thumbnail and lower-pixel rules. Invalid supplied inputs fail acceptance; they
are not silently dropped. No client thumbnail upload is required. If missing,
automatic optional image enrichment derives a thumbnail from typed image/video
main bytes; raw documents/audio/voice are never classified by sniffing. The owner
may publish the validated main before generation completes, or with no generated
size at all. Generation failure does not fail or reverse successful publication.
There is no synchronous worker method or separate optional-generation status API.

### Independent representation revision and recovery

New `Photo`, `Document`, `ProfilePhoto`, `UserPhoto`, `ChatPhoto` and `StickerView`
report positive `representation_revision`, initially 1, even with no thumbnail.
The owner atomically links durably ready output IDs and increments only that
revision; it never replaces an adopted client thumbnail. Main identity/bytes,
measured facts, authored preview, message `body_revision`/`edit_date`, asset version,
gallery revision and pack revision do not change for enrichment. Equal revisions
describe identical complete sets. Compare only within the same principal, exact
owner/version and immutable main; stale jobs cannot attach to replacements.
Every read checks **exact per-output membership**, **never all children** of a
processed main. A ready generated output grants nothing until explicitly linked
to that particular owner. Removal/replacement/visibility changes revoke the
context on the next file read.

Older objects and message captures have absent representation revisions and stay
frozen; do not enrich them or widen their grants. New sends of existing catalog
assets capture the exact main/version and explicit current output membership;
later catalog enrichment never implicitly widens that message capture. New sends
may capture older assets without modifying them. Reusing an older retained gallery
entry does not retrofit its source or representation policy. Optional sizes never
gate pack publication or increment the pack's authored revision.

Message enrichment uses `TARGET_CHANGE_KIND_REPRESENTATION`, additive
`TargetChange.representation_revision` and `MessageChanged.representation_revision`.
It creates a retained mutation position, **not** an authored edit; body revision
stays unchanged. Existing `GetMessages`, `GetHistory` and `ListMessageChanges`
hydrate complete currently authorized representations. Resume only from the
existing stable change cursor; compare body and representation revisions
independently and never merge representations across an edited/replaced main.
`ChatPhotoRepresentationChanged` (group/channel exact `chat_id`),
`ProfilePhotoRepresentationChanged` and `StickerAssetRepresentationChanged` are
visibility-filtered hints; fetch `GetChats`/`GetChannels`, `GetProfilePhotos` or
exact `GetStickerAssets`. Actor-only `ChatPhotoUpdateChanged`,
`ChannelPhotoUpdateChanged`, `ProfilePhotoUpdateChanged` and `AssetChangeChanged`
still hint their corresponding domain queries. Query those on startup or
reconnect, and query again if another hint arrives during a fetch. Stopping
observation does not cancel pending work.

For immediate file-backed sends and albums, `SendStatusChanged` is an actor-only
hint to refresh with `MessagesService.GetSendStatus`. It can arrive out of order
or be missed. Recover unresolved sends on startup and reconnect using the
original target and key (any original member key for an album). Query again if a
hint arrives during a fetch. Missing status after an ambiguous send does not
prove failure or permit a fresh key. The hint does not grant body or file access.

For both sends and chat-photo updates, while connected, schedule a fallback query
30 seconds after an ambiguous mutation response or a nonterminal status, even
if no hint arrives. Use the original binding: `GetSendStatus` for sends and
`GetChatPhotoUpdate` with the original `chat_id` and `operation_id` for chat photos.
Restart the 30-second timer after each query that leaves the outcome unresolved.
Keep at most one status query in flight per operation and stop the timer once a
terminal outcome is known.

## Authorization

File access flows from the application objects that reference a file —
messages, profile photos, chat photos, sticker packs, Dailies, and Posts — and
from the uploader's own authorization. A `file_id` grants no access by itself:
resolution requires an authorized application object or uploader authorization, so a bare
`file_id` obtained from any other source — for example an export or a
guess — must not resolve. Servers report unknown and inaccessible files
identically, and upload sessions of other principals are indistinguishable
from unknown sessions. The same rules apply to thumbnail files:
a `ThumbnailSource` or `Thumbnail` file
reference is access-checked like any other file. Runtime enforcement lives
in the server implementation, not in this contract.

`GetFileInfoRequest.file_access_context` and
`DownloadPartRequest.file_access_context` carry the reference for these checks.
Select exactly one of `MessageFileReference` (conversation and message ID),
`ProfilePhotoReference` (user and gallery-entry ID), `StickerAssetReference`
(unified asset ID and exact version), `ChatPhotoReference` (chat and current
photo ID), `daily_id`, or `post_id`. The requested `file_id` must identify a
main file or its explicitly linked thumbnail in the exact object or asset
version selected by the context. With no context, only the uploader can read
their own completed file. A supplied context is checked even for the uploader;
it cannot authorize an unrelated file or fall back to uploader identity or another object.
A metadata response does not grant future downloads:
each range call checks visibility again, including deletion/revocation, photo
selection/privacy, and pack unpublication. Unknown and inaccessible references
and mismatched file membership have the same not-found outcome.

The [Daily and Posts contract](/schema/daily-and-posts) defines file
contexts scoped to `daily_id` or `post_id`. If both objects reference the same
media file, check the object named on this read. A visible Post does not extend a
viewer's access through an expired Daily.

`FileAccessContext.chat_photo` in `tinkle/v1/files.proto` references a positive
chat/group/channel `chat_id` and the current `ChatPhoto.photo_id` from
`tinkle/v1/messages.proto`, not a file ID. `ChatPhoto.file_id`, `metadata` and
`thumbnail` describe the current main file and optional completed thumbnail. The contract requires every
`GetFileInfo` and `DownloadPart` call to check current chat visibility and that
the requested file is that current photo's main file or its linked thumbnail in that
chat. Replacement, removal, or lost visibility invalidates the context on the
next call; no historical chat-photo gallery is promised.

## Authored assets and profile photos

`StickersService` owns both sticker and custom-emoji assets and their same-kind,
user-owned packs; there is no separate emoji service. `GetStickerAssets` batches
asset IDs, including custom-emoji IDs from message entities and reactions.
ID-only lookup resolves the current usable head; exact `AssetReference` pairs
never substitute another version. Packs pin at most 100 exact asset versions,
and publication never advances those pins to head. Owner mutations compare
`expected_version` or `expected_revision` atomically; conflicts have no effect.
Withdrawal removes new catalog grants, not exact files already captured by a
message. Exact lookup with `message_reference`, and file reads with that message
context, require current message visibility. They never confer new-send access,
access to a different version, or a permanent grant. Installation alone is not
authorization. Unavailable emoji render as retained plain-text fallback.
`AccountService`
sets, lists, selects, and deletes profile photos. The owner gallery is bounded
at 10 entries and rejects insertion when full; nonowners see only the selected
photo when privacy permits it. Deleting a gallery entry does not delete files
used elsewhere.

The owner's gallery listing includes a consistent `gallery_revision`; mutations
require its positive value as `expected_revision`. Nonowner listings omit the
revision to avoid disclosing hidden gallery changes. Matching no-ops preserve
the revision, changes increment it once, and stale attempts fail without effect.
Repeated sets of an identical retained file/source reuse the gallery-entry ID;
they do not append duplicates. After a timeout, refetch and reconcile the source
and selection rather than retrying with a fresh token. Recover ambiguous sets
through the original `request_id`; deletion never makes that ID reusable.

`StickerAssetSource` and `ProfilePhotoSource` require `MediaValidation` with
`MEDIA_VALIDATION_PROFILE_STRICT_LOSSLESS`, version `1`. Raw upload completion
does not validate application media. Authoring verifies the complete source and
any supplied thumbnail before making the object visible. Optional generated
thumbnails do not gate publication. This profile accepts
static PNG and lossless WebP, not TGS, WebM, APNG or lossy WebP.
WebP can animate: format and animation metadata are independent. GIF input must
be normalized by the client to supported lossless bytes; do not silently flatten
animation or use lossy encoding. Profile photos must be static, at most 4096x4096
and 10,000,000 bytes. Sticker mains are at most 512x512; custom emoji at most
128x128. Static asset mains are at most 1 MiB; animated mains at most 4 MiB,
3000 ms and 180 frames. These bounds apply in addition to format validation.
Accept at most one optional static thumbnail input per authored
asset/photo under the purpose table above. Invalid supplied inputs are rejected,
never silently discarded. Exact decoded bounds live in the source-message
comments in the generated reference. Servers do not transcode mains.

The contract also exposes no global existence oracle for content digests.
An implementation may address storage by content hash internally, but no
method reports "these bytes exist somewhere" for an arbitrary digest —
content addressing must never become a way to probe what other principals
have uploaded.

## Errors

Every failure falls into a small set of conditions. The table pins the
condition for each method and situation; concrete status codes and
error-detail mechanics are transport bindings, defined by the
implementation repositories, not by this page.

| Method | Condition |
| --- | --- |
| `BeginUpload` | Malformed or inconsistent request — negative or oversized `size_bytes`, missing key, wrong digest length, or a declared digest that cannot match a zero-byte upload |
| `BeginUpload` | Same key, conflicting parameters |
| `BeginUpload` | Per-principal session or retention limits |
| `UploadPart` | Wrong part size, out-of-range index, or wrong digest length |
| `UploadPart` | Conflicting bytes for an already-confirmed index, including concurrent conflicting submissions |
| `UploadPart` | Session is terminal (completed, aborted, or expired) |
| `UploadPart` | Negotiated parallelism or resource limits exceeded |
| `GetUploadStatus` | Invalid, foreign, or expired continuation token |
| `CompleteUpload` | Missing parts — `IncompleteUploadError` attached to the error where the transport supports structured error details |
| `CompleteUpload` | Digest expectation disagrees with the server-verified digest — retryable when supplied by `CompleteUpload`, permanent when declared at `BeginUpload` |
| `CompleteUpload` | Session is terminal (aborted or expired) |
| `GetFileInfo`, `DownloadPart` | Unknown **or** inaccessible file (authorization-safe) |
| `GetUploadStatus`, `UploadPart`, `CompleteUpload`, `AbortUpload` | Unknown **or** foreign session (authorization-safe) |
| `DownloadPart` | `offset` beyond the size, nonpositive limit, or — when advertised — a limit above `max_download_part_bytes` |
| `DownloadPart` | Current transfer budget exhausted |
| All methods | Deadline exceeded or transport unavailable — ambiguous, never rollback |

Three rules apply across the table:

- **Malformed input never consumes an idempotency key.** Requests rejected
  as malformed are validated before idempotency binding, so they can never
  conflict with a retained session.
- **Digest mismatches never publish the file and never terminate the
  session.** A `CompleteUpload`-supplied mismatch is correctable by
  retrying with a corrected expectation; an unsatisfiable `BeginUpload`
  declaration never is — the client aborts and starts over.
- **Timeouts and cancellation are ambiguous, never rollback.** No status
  or transport cancellation reverses a committed part or a committed file;
  recover through `GetUploadStatus` and idempotent retries.

## Implementation defaults

Part-size selection within the four allowed sizes, parallelism, session expiry,
download limits and upload-session retention are deployment configuration. Domain
pending full outcomes have the minimum 30-day retention described above. Clients must
honor the values returned by `BeginUpload` and
`GetFileInfoResponse.max_download_part_bytes` instead of assuming
defaults, and must treat all of them as potentially different on the next
deployment.
